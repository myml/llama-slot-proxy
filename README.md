# llama-slot-proxy

[English](README.en.md) | **中文**

**给本地大模型加一层记忆：算过的东西不再重算，新开一个对话、或者服务重启之后，都能立刻接着用。**

---

## 先说效果

跑本地大模型，最影响体验的往往不是"生成得慢"，而是**等**：等它把你之前发过的内容从头再读一遍。
这个代理把这些内容算完的状态存下来，下次直接用。

| 场景 | 不用它 | 用它 | |
|---|---|---|---|
| **服务重启后，继续刚才那个对话** | 等 **10 分钟** | 等 **5 秒** | **快 122 倍** |
| **新开一个对话**（系统提示词相同） | 等 **53 秒** | 等 **23 秒** | 少算 **59%** 的内容 |
| 同一个对话的下一轮 | 4.8 秒 | 4.8 秒 | 本来就快，代理不添乱 |

> 数字来自一段真实的 agent 对话（约 10.4 万 token），机器是 Ryzen AI MAX+ 395 / Radeon 8060S，
> 模型是 27B 混合模型 4-bit 量化、256K 上下文。详细复现条件见下方「实测数据」。

**它帮不上忙的情况**也说清楚：如果你的对话很短（几百 token），或者客户端每轮都会改写历史，
那省下的时间可以忽略 —— 这种情况下代理基本是透明的，不会有副作用，但也没必要专门装它。

**最后一行同样重要**：代理只在"该出手时"出手。同一个对话连续提问时，它会**刻意什么都不做** ——
因为那时候本来就快，多此一举反而更慢（详见「什么时候代理会故意不动手」）。

## 为什么会慢

和大模型对话，客户端每一轮都会把**整段对话重新发一遍** —— 系统提示词、工具定义、以及全部历史。
如果这是个 agent（比如帮你写代码的助手），光是系统提示词就可能三万多字，
再加上几十轮工具调用的记录，一次请求几万到十几万 token 是很正常的。

好消息是 llama.cpp 自己会缓存已经算过的前缀，所以**同一段对话的下一轮**非常快。

坏消息是这个缓存**活在内存里**。只要发生下面任何一件事，之前算的全部作废，得从头再读一遍：

* 你**新开了一个对话** —— 哪怕系统提示词一模一样
* **服务重启**了，或者你改了启动参数
* 你在**两个对话之间来回切换**，缓存被另一个挤掉了

对一个十万 token 的对话来说，"从头再算"就是**十几分钟的干等**。而这三件事，
在日常使用里几乎天天发生。

## 它是怎么做到的

存两种"算好的状态"。它们是 llama.cpp 原生的状态文件，代理只是负责在合适的时机让服务端存和读。

* **种子** —— 只把**系统提示词**（含工具定义）算完的状态，别的都不含。
  因为所有共用这份系统提示词的对话，开头都是它，所以**一份种子对它们全都有效**。
  它按内容取指纹，所以系统提示词一改，自动就是一份新种子，不需要你手动维护。

* **会话快照** —— 某一整段对话聊到哪儿算到哪儿的状态。
  只对这段对话有效，因为同一段对话的后续提问是它的延续。

每次请求按「从便宜到贵」的顺序处理：

1. **是个小请求吗？**（比如客户端顺手生成一个标题）→ 直接放过，完全不碰缓存。
2. **这个对话的状态已经在内存里了吗？** → 直接转发，什么都别做。后续交给 llama.cpp 自己。
3. **有这段对话的快照、而且比种子更深吗？** → 恢复它。
4. **有种子吗？** → 恢复种子。
5. **都还没有？** → 先把种子算出来（一次预填充），然后转发。

## 实测数据

开发机：Ryzen AI MAX+ 395 / Radeon 8060S，61 GiB 统一内存；
27B 混合模型，4-bit 权重，`q8_0` KV，256K 上下文，单槽位（`-np 1`）。
以下是一段真实的约 10.4 万 token 的 agent 对话：

| | 需要重算的 token | 墙钟耗时 |
|---|---|---|
| **冷启动**，完全无缓存 | 103,928 | **608.6 s** |
| 同一对话的下一轮 | 19 | **4.8 s** |
| 同一对话，**重启 llama-server 之后** | 18 | **5.0 s** |

新开一个对话、共用同一份系统提示词、上下文约 1.38 万 token 时：

| | 需要重算的 token | 墙钟耗时 |
|---|---|---|
| 无缓存 | 13,789 | 52.8 s |
| 恢复种子 | 5,604 | **22.9 s** |

下面是**生产环境真实流量**的统计：从代理日志里取出连续 10 个真实新会话（系统提示词
8,185 token，真正的用户消息只有几十 token）。

| | 需要重算的 token | 墙钟耗时 |
|---|---|---|
| 新会话，无种子（同一日志里未命中的请求） | 8,267（全量预填充） | 38.5–67.8 s |
| 新会话，命中种子（10/10 个真实会话） | **82** | **6.2–12.0 s** |

也就是说：**系统提示词那 8,185 个 token 被完整复用，真正要算的只剩 82 个。**

恢复本身很便宜：一份 640 MB 的状态文件约 130 ms 读完。本机上状态文件大小服从

```
状态字节数 ≈ 149.63 MiB + 34.0 KiB × n_tokens
```

所以满 256K 上下文时每份状态文件约 8.65 GiB。请据此规划 `-max-bytes`。

## 什么时候代理会故意不动手

这一点值得单独说，因为它决定代理是"帮忙"还是"添乱"。

llama.cpp 在两次请求之间**本来就保留着槽位里的状态**。所以当某个对话的状态**已经在内存里**、
而你只是接着问下一句时，再去做一次恢复是纯浪费：

* 要花时间把一份几百 MB 的状态文件读回来（640 MB 大约 0.13 秒）；
* 更要命的是，**它会毁掉 llama.cpp 进程内的上下文检查点** ——
  而那正是提示词尾部被替换时（重试、编辑、改分支）服务端能廉价回滚的依仗。

连续提问实测：两种做法处理的 token 数完全相同，但多做一次恢复每轮要多花约 0.4 秒。
所以代理的第一快路径是「直接转发，什么都别碰」。这一点也是它和 llama.cpp 自带的
上下文检查点（`-ctxcp`、`-cms`）能配合而不是互斥的原因，详见最后一节。

## 前置条件

* 一个带 `--slot-save-path` 选项、以及 `/slots?action=save|restore` 接口的 llama.cpp 构建
  （上游早已具备）。
* **llama-server 必须写入代理所读取的同一个目录。** 代理只把一个**文件名**交给服务端，
  由服务端相对它自己的 `--slot-save-path` 解析。所以 `-cache-dir` 在两边必须是同一个路径 ——
  同一台主机、同一个挂载命名空间、同一个字符串。
* 假定单槽位（`-np 1`）。代理把缓存操作串行化在一把全局锁后面，因为恢复会覆盖槽位里现有的内容。
* 别无其它要求。不需要 cgo、不需要第三方模块、不需要构建服务。

## 快速开始

启动 llama-server 时给出 slot-save-path（推荐 tmpfs，原因见下方「为什么用 tmpfs」）：

```bash
llama-server -m model.gguf -c 32768 -np 1 \
  --slot-save-path /dev/shm/llama-slot-proxy
```

在它前面启动代理，然后把客户端指向代理：

```bash
llama-slot-proxy \
  -listen 0.0.0.0:8080 \
  -upstream 127.0.0.1:8081 \
  -cache-dir /dev/shm/llama-slot-proxy \
  -persist-dir /var/lib/llama-slot-proxy
```

**建议先用 `-dry-run -v` 跑一次**：这时代理退化为纯透传，但仍会把每个上游响应的
`cache_n` / `prompt_n` 记进日志 —— 这是最快看出你的负载能省多少的办法，而且不会有任何副作用。

### 构建

```bash
make build          # 或者：go build -o llama-slot-proxy .
```

需要 Go 1.21+。除标准库外没有任何依赖。

## 命令行参数

| 参数 | 默认值 | 含义 |
|---|---|---|
| `-listen` | `0.0.0.0:8080` | 监听地址。 |
| `-upstream` | `127.0.0.1:8081` | llama-server 地址。 |
| `-cache-dir` | `/dev/shm/llama-slot-proxy` | 工作目录。**必须等于** llama-server 的 `--slot-save-path`。 |
| `-persist-dir` | `""` | 持久目录：退出时收到一份副本，被淘汰的快照也移到这里。留空则全部留在 `-cache-dir`。 |
| `-max-bytes` | 16 GiB | `-cache-dir` 的容量上限。 |
| `-durable-bytes` | 32 GiB | `-persist-dir` 的容量上限。 |
| `-max-age` | 24h | 超过这个年龄的会话快照会被丢弃。 |
| `-max-seeds` | 4 | 保留多少个不同的种子。 |
| `-session-header` | `Session_id` | 携带会话 id 的请求头；找不到时回退尝试 `X-Client-Request-Id`。 |
| `-min-system-bytes` | 2000 | system 消息短于该字节数的请求完全不走缓存（用来过滤辅助请求）。0 = 全都缓存。 |
| `-require-stream` | false | 额外要求 `stream: true` 才缓存。 |
| `-save-every-tokens` | 8000 | 内容增长到这么多 token 后保存一次会话快照。0 = 只在槽位换手时保存。 |
| `-save-every-msgs` | 10 | 新增这么多条消息后保存一次。0 = 关闭。 |
| `-lock-wait` | 120s | 等待槽位锁的上限；超时则不加锁直接转发。 |
| `-log` | `""` | 日志文件；留空则写 stderr。 |
| `-dry-run` | false | 完全不碰缓存（纯透传）。 |
| `-v` | false | 详细日志。 |

## 什么时候保存

状态文件很大（几百 MB），所以代理**不会**每个请求都存：

* **换手时保存。** 当另一个对话即将占走槽位时，先把当前这段存下来。
  这是它的状态还能被捕获的唯一时刻，也是**稳态提问完全零磁盘写入**的原因。
* **按内容增长保存。** 一直占着槽位的对话，在提示词增长到 `-save-every-tokens` 个 token、
  或 `-save-every-msgs` 条消息时保存一次。按**内容**而不是按时间，
  所以空闲时不会白白写盘，突发提问也不会漏掉。
* **退役。** 一份快照如果被恢复、却**没有**真正被复用，那它比没有快照更糟 ——
  因为那次恢复毁掉了 llama.cpp 本来可以用来回滚的检查点。连续两次没命中就把它丢掉。
  另外，如果一份种子已经能覆盖某个快照，也会把它丢掉（留着只占地方，换不来什么）。

启动时**不做任何预热**：只有请求真的需要时，才从 `-persist-dir` 把快照取回来。

## 为什么用 tmpfs

状态文件又大、又反复重写，所以直接写盘既慢、写放大又严重。开发机实测：

| 介质 | 写入 2 GB |
|---|---|
| tmpfs（`/dev/shm`，即内存） | 0.25 s（8.7 GB/s） |
| loop 设备上的 ext4（即磁盘） | 2.07 s（1.0 GB/s） |

所以工作目录放在 tmpfs（内存里），而 `-persist-dir` 是一份持久化的副本：
优雅退出时刷新一次，同时用来存放被工作集淘汰的快照。
只复制改动过的文件，而且每次复制都先写 `*.tmp` 再改名，
所以中途被打断也绝不会弄坏一份快照。

收到 `SIGTERM`/`SIGINT` 时，代理会先等在途请求结束（避免在生成中途捕获槽位），再落盘。
`SIGKILL` 和断电则会丢失还没刷新的部分 —— 这是 tmpfs 的固有取舍。

## 注意事项

部署前请读一遍。

* **客户端必须逐字重发历史。** 这里的一切都建立在「已保存的内容是下一个请求的严格前缀」
  之上。裁剪、摘要、或改写早期轮次的客户端，只会错过缓存。这是安全的（服务端会退回到
  正常的前缀匹配，代理也会退役反复没命中的快照），但确实意味着没有收益。
* **同一个 session id 下重发同一段对话时，会退回到种子。** 快照是**响应之后**保存的，
  所以它拿着的状态是「提示词 + 已生成的内容」—— 必然比产生它的那次对话更深。因此只有
  **消息条数严格更多**（追加了内容）的请求才可能复用它。代理按记录的消息条数判断：
  条数**不比快照多**就跳过快照、改用种子。这覆盖两种常见情形 —— 复用同一 session id 开新对话，
  以及**重试/重新生成**（同一段对话重发，条数相同，但快照已经越过了它的末尾）。
  从干净缓存和从「上一轮跑完留下的深快照」开始，端到端回归的结果现在完全一致。
* **状态文件会被解析文件头。** 代理读取前 12 字节（magic、version、token 数），
  以便在不恢复的前提下比较候选。如果 llama.cpp 改了那个磁盘格式，代理会把文件视作不存在 ——
  这是优雅降级而非崩溃，但缓存在更新解析逻辑之前会失效。
* **快照大小会被合理性检查**，依据是 `149.63 MiB + 34.0 KiB × n_tokens`：
  一次「空间不足」的保存会留下截断文件，而它的文件头仍然声称完整的 token 数。
  远低于估算值的文件会被忽略。这组常数来自某一个混合模型，只用作下限，不是精确校验。
* **`-min-system-bytes` 很重要。** 很多客户端会把同一个 session id 复用于一些小的旁路请求
  （生成标题之类）。它们很短的 system 提示词会构建一个没用的种子，并留下一个浅快照，
  下一轮污染真正的对话。默认值会把它们过滤掉。
* **单槽位。** 在 `-np 1` 下恢复会覆盖常驻状态，代理据此串行化。多槽位未被建模。
* **缓存键里包含模型指纹。** llama.cpp 的状态文件只记录**架构名**，读取时也只比对架构名
  —— 上游源码在写入侧和读取侧各留了一条 `TODO: add more model-specific info which should
  prevent loading the session file if not identical`。所以换成一个**同架构、同尺寸、不同权重**的
  GGUF 时，旧状态会被无错加载，然后**拿上一个模型的 KV 去回答**：是静默的错答案，不是崩溃。
  代理因此把 `/props` 的 `model_path`、`model_ftype`，加上模型文件的大小与 mtime，一并折进缓存键。
  换模型会让每个缓存条目自动改名，旧条目变成没人引用的垃圾，由既有的淘汰逻辑清掉 ——
  **不需要手动清理**。（状态文件的格式版本号由 llama.cpp 自己校验，见
  `LLAMA_STATE_SEQ_VERSION`，所以升级 llama.cpp 是安全的。）
* **流式响应是逐块 flush 的。** 上游每个 SSE 事件一到就转发出去。这在短回答上差别很大：
  若攒在响应缓冲区里，一个不到 2 KB 的流会等到整段结束才一次性到达客户端。
* **代理只关乎速度，不关乎正确性。** 即使所有缓存操作都失败，它也会原样转发请求。
  不存在任何一条「缓存失败会改变响应内容」的路径。

## 与 llama.cpp 上下文检查点的关系

代理与 llama.cpp 自己的上下文检查点（`-ctxcp`、`-cms`）解决的是**重叠但不同**的问题，
它们可以叠加使用：

* 代理负责**整块状态复用** —— 新对话，或槽位被抢占、服务重启后的对话，从一份已保存的前缀重新起步。
* 检查点负责**对话内部的回滚** —— 例如提示词尾部被替换时（重试、编辑、改分支），
  只复用一段后缀，而不是整块。

两者都值得保留。这也是上一节「什么时候代理会故意不动手」的另一个理由：
一次槽位恢复会替换掉提示词状态，所以当对话已经常驻时，代理会刻意不做恢复，
以免白白丢掉服务端进程内的检查点。
